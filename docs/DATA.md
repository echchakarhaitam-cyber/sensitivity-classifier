# Data

sensclf uses two public, **fully synthetic** PII datasets. The text, people, organisations
and identifiers were generated by language-model pipelines; no record describes a real person.
Nothing is redistributed: the raw parquet files stay outside this repository (or in
`data/raw/`, gitignored), derived sets are written to `data/processed/` (gitignored), and only
metadata is committed: `data/manifest.json` (pinned revisions, sizes, SHA-256 hashes) and
`results/data_stats.json`.

Every number on this page is generated by a script (blocks between `<!-- name:begin -->` and
`<!-- name:end -->` markers); prose contains no measured values.

## Access, verification and reuse of privgate

The raw files are the ones already downloaded for our public library **privgate**
([llm-privacy-gateway](https://github.com/echchakarhaitam-cyber/llm-privacy-gateway), pinned
dependency at commit `498adccdf1cb5c4b3340a20293a88104fa678fcc`). They are read from
`SENSCLF_RAW_DIR` (default `../llm-privacy-gateway/data/raw`), in privgate's layout
`<dir>/<owner>__<dataset>/<file>`.

- `data/manifest.json` → `files` is copied unchanged from privgate's manifest at that
  commit (repo, revision, path, size, SHA-256, licence, pinned URL).
- `sensclf.rawdata` hashes every raw file before use and **aborts on any mismatch**. A missing
  file is downloaded from its pinned URL (the revision is part of the URL), via a `.part` file,
  and must then match the recorded size and hash.
- Parsing reuses privgate: its parquet reader, its Nemotron/Gretel span parsers, document ids
  and `Document`/`Span` model, and its group-aware split hashing (`docs/TASK.md`, splits).
  sensclf adds only a small adapter that keeps the **raw** label of each gold span, because
  privgate's `Document` stores mapped entity types and the sensclf categories are defined on
  raw labels.

Reproduce:

```
pip install -e ".[dev]"
python scripts/build_sets.py     # verify raw files, write data/processed/*.jsonl + hashes
python scripts/data_stats.py     # results/data_stats.json and the tables on this page
pytest -q -m data                # integration tests on the real files
```

## Schema facts relied upon

(Inspected and documented in privgate's docs/DATA.md at the pinned commit; restated here.)

- **Nemotron-PII**: string columns `uid, domain, document_type, document_description,
  document_format, locale, text, spans, text_tagged`; `spans` is a string (Python literal or
  JSON) holding `{start, end, text, label}` dicts. Each `uid` occurs twice per file (`locale`
  `us` and `intl`: two renderings of one persona), so `doc_id` is `nemotron:<uid>:<locale>`
  and `uid` is the `group_id` used for splitting. Train and test files share no uid and cover
  almost disjoint `domain` values: the test file is domain-shifted.
- **Gretel English files**: `generated_text`, `pii_spans` (a JSON string of
  `{start, end, label}`; no covered text, so only bounds are checked), descriptive columns and
  the pandas index `__index_level_0__`, used as `doc_id` (`gretel:<n>` for the test file,
  `gretel-train:<n>` for the train file, whose index restarts at 0).

## Gretel train/test duplicates

Some Gretel train documents have exactly the same `generated_text` as a Gretel test document
(privgate found 11). `scripts/build_sets.py` recomputes the overlap (SHA-256 of the text) and
drops those documents from `gretel_pool`, so no test text can ever enter training; the count
it finds is recorded in `data/manifest.json` (`gretel_pool_dropped_duplicates`) and below.
